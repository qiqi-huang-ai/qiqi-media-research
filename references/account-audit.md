# 单账号审计协议

当用户给出公开账号主页并说“分析这个博主”“看看这个账号”“拆一下对标账号”等，使用本协议。即使提示词很短，也交付完整账号审计；不要只输出基础画像和 Top 作品。

## 默认研究目标

判断这个账号：做什么、靠什么获得表现、什么是稳定模式、什么只是单条异常值、哪些部分适合用户借鉴，以及下一步应如何小规模验证。

## 最小成熟证据链

1. 账号公开资料：昵称、简介、粉丝、作品、累计获赞、关注和主页链接。
2. 至少一页近期作品；记录样本实际首尾日期。置顶旧作可纳入代表作品，但不得混入“近期更新频率”。
3. 抖音作品用独立统计端点补取真实播放量；缺失保持空值。
4. 建立账号内基线：播放/点赞中位数、互动率中位数、时长和更新节奏；不要只给均值。
5. 按可用主指标分出前 25%、中间样本、后 25%，比较题材、标题信号、时长和互动构成。
6. 从 2 条高表现作品和 1 条中位表现作品抽取公开评论，统计需求类别和覆盖作品数。评论不可用时明确跳过，不根据标题臆测用户痛点。
7. 标题/文案采用多标签分类，逐类给出作品数和表现中位数；只有一条命中的类别只能写“个案”。

## 报告必须包含

- 账号一句话定位：基于简介和近期作品，不使用“头部”“行业第一”等无横向基准标签。
- 账号事实与样本边界。
- 更新节奏和表现基线。
- 高表现、普通、低表现三组对照。
- 内容组合：主题数量、占比或多标签计数，以及各组表现。
- 文本层钩子/标题模式：标注为标题文案分析，不冒充真实前三秒。
- 评论需求：样本量、类别计数、覆盖作品数和少量代表性原话。
- 稳定规律与偶发爆款分开陈述。
- 可复制、谨慎复制、当前无法验证三类结论。
- 3–5 条带基线和验证方式的行动建议。

## 交付硬门槛

`research_runner` 输出的是有证据链的分析草稿，不是只能交付的数据导出。最终 Markdown 必须经过一次面向用户的结论整理，但不能修改原始数值。正文至少应有 18 条证据化发现，并同时包含：

- 近期/历史样本分界和只用近期样本计算的更新节奏；
- 内容组合与文本层标题钩子的分类表现；
- 稳定规律、偶发爆款、可复制、谨慎复制和当前无法验证；
- 评论覆盖、类别计数、代表原话和至少 3 条可执行建议。

`delivery_audit` 会检查这些内容。如果只有账号画像、Top 作品和一条笼统建议，必须返回 `failed`，不得包装为成熟分析。

## 禁止的捷径

- 不用赞粉比推断流量来自推荐流。
- 不根据关注数推断“单向输出型”等人格或运营方式。
- 不在没有同类账号样本时声称“头部”“中上水平”。
- 不用作品标题推断真实画面形式、前三秒、完播率或完整内容结构。
- 不把累计播放不同年龄的作品直接解释为近期上升或下降；需要趋势时使用同一时间窗口或日均指标。
- 不从多标签数量直接推导互斥内容占比。
- 不给没有计算过程的 70/30、80/20 等策略比例。

## 默认交付判定

`analysis/delivery-audit.json` 必须同时通过：账号资料、表现基线、标题/文案模式、高低表现分组、可执行建议和内部证据台账。任何一项缺失，都不能把结果包装成成熟账号分析。
